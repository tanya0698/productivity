# ADR 0003: Authentication

**Status:** Decided — Supabase Auth
**Date:** 2026-10-21, decided 2026-11-06

## Decision

Sign-in uses **Supabase Auth** (email and password), from the same Supabase project as the database (ADR 0002).

- **Clients:** the web and Android apps use `supabase-js` for **sign-in only**: sign in, create account, password reset (web), sign out. They never query tables with it; data goes through the API's `/api/sync` (ADR 0002).
- **Sessions:**
  - **Web:** kept in browser storage under `productivity-auth`.
  - **Android:** kept in `expo-secure-store`, split into chunks because SecureStore items are capped at about 2 KB and a session is larger.
  - **Refresh:** `supabase-js` refreshes tokens; Android only does so while the app is in the foreground.
- **API:** a global `AuthGuard` (`apps/api/src/common/auth.ts`).
  - **Checks:** it verifies `Authorization: Bearer <token>` against the project's **public JWKS**. The project signs with an asymmetric ES256 key, so no shared secret lives on the server. The issuer must be `<SUPABASE_URL>/auth/v1` and the audience `authenticated`.
  - **Users:** the token's `sub` is the user id. The `users` row is created on first sight.
  - **Open routes:** marked `@Public()`; only `/api/health` today.
- **Local data is per account.** Each user gets their own IndexedDB database (`productivity-<userId>`) and SQLite file (`productivity-<userId>.db`), so two accounts on one device never see each other's notes, and signing back in finds your data still there.
- **Development stand-in.** With `ALLOW_DEV_USER=true`, a request *without* a token acts as `DEV_USER_ID`; `npm run sync:check` relies on it. It never applies when a token is sent (a bad token is always a 401), and never with `NODE_ENV=production`. `.env.example` ships it as `false`.

## Why

- Standalone from City Parking's UnifiedAuth, at no extra cost, and next to the database.
- Asymmetric keys mean the API holds nothing that could forge a session.
- Email/password, magic links and social sign-in are all available later without changing the API.

## Verified (2026-11-06)

Against the running API:
- `/api/health` is public.
- No token is refused (401), or acts as the dev user only when `ALLOW_DEV_USER=true`.
- A malformed token is refused, even with the dev switch on.
- An ES256 token with the project's real key id but signed by a different key is refused.

Web tests cover signing in, being sent to sign-in when signed out, and signing out. A real sign-in end to end still needs the Supabase settings below.

## Supabase settings this depends on

- **Authentication → URL Configuration:** Site URL and Redirect URLs include `http://localhost:5173` (and the production address later). Confirmation and reset emails link there.
- **Authentication → Sign In / Providers:** Email enabled. With "Confirm email" on (the default), new accounts must click the emailed link before signing in.

## Not done yet

- Signing in on Android hasn't run on a device (it typechecks and bundles).
- No social sign-in, no "change email", no account deletion screen.
- Data created as `DEV_USER_ID` before auth existed stays owned by that stand-in user.
