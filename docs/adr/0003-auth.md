# ADR 0003: Authentication

**Status:** Open (decide in Phase 0). Leading option: Supabase Auth.
**Date:** 2026-10-21, updated 2026-10-22

## Context

None of the apps have sign-in yet. The API runs every request as `DEV_USER_ID` and refuses all requests when `NODE_ENV=production` (`apps/api/src/common/current-user.ts`). The web and Android apps open straight into the app.

The database runs on Supabase (ADR 0002), which makes Supabase Auth available at no extra cost.

## Options

1. **Supabase Auth (leading).**
   - **Why:** standalone, with email/password, magic links and social sign-in built in, and it already sits next to the database.
   - **API side:** verify Supabase's access tokens against the project's JWKS. The `sub` claim becomes the user id, so `CurrentUser` becomes a few lines.
   - **Clients:** the web and Android apps use `supabase-js` for sign-in only, with no table queries (ADR 0002). Android stores the session in `expo-secure-store`.
2. **NestJS `identity` module.** Fully self-built, but the most to build and secure yourself (password hashing, refresh rotation, rate limits; plan §10).

## Decision

_Not yet made._ Whatever is chosen replaces the body of `CurrentUser` in `apps/api/src/common/current-user.ts`, and `users.id` becomes the identity provider's user id.
